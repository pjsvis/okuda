# Brief: Per-token baselines — the count-parity swap hole, closed

**Created:** 2026-11-05
**Status:** Done — shipped 2026-11-05: both gates judge per token, `ADR-ALLOWANCE-NAMES-REFERENT-084` accepted, 1035 tests green, `just check` rc=0.
**Debrief:** `DBF-ALLOWANCE-REFERENT`

## Lineage

`BRF-CALLSIGN-CHECKSUM` shipped both citation gates with a per-file **count**
baseline, and its review closed the stale-entry half (`verdict(0, N)` is a
shrink) while filing the other half as deliberate scope: *a same-edit
count-parity swap passes both gates*. This brief is that scope, taken.
The ratchet idiom itself is `ADR-RECORD-LINKAGE-065`; the shape this brief
settles is `ADR-ALLOWANCE-NAMES-REFERENT-084`.

## The hole, stated exactly

Both gates grandfather sediment as `{file: count}`. The verdict compares one
number against one number, so a file may **drop** a grandfathered citation and
**gain** a different one in the same edit and read `ok` — the count is the only
witness, and the count did not move. The allowance is a *quantity*, and a
quantity cannot say *which*.

The failure is not hypothetical shape: the checksum's own review demonstrated
the count-parity pass live (`debriefs/2026-10-02-debrief-review-cadence.md:70`).

## The fix

The baseline becomes `{file: {token: count}}` — a **set with multiplicity**,
not a total. Each gate then judges three deltas instead of one:

| Delta | Meaning | Verdict |
|---|---|---|
| token absent from the file's baseline, any count | a new citation | **violation** |
| token over its own grandfathered count | a repeated citation | **violation** |
| token under count, or gone | the prune | shrink |
| nothing moves | at baseline | ok |

The count verdict is **subsumed**, not dropped: if the total rises, by
pigeonhole some token rose, and the token verdict reports which. That is the
whole gain — the gate keeps every verdict it had and names the referent.

Tokens are normalised per gate: td IDs lowercase (the pattern is
case-insensitive, `scripts/td-id-lint.ts:14`, so a case flip must not read as a
swap); callsign families are already uppercase-only by construction.

**One core, two gates.** `judge()` and `tally()` live in `scripts/td-id-lint.ts`
beside the existing `scannedFiles()`/`verdict()` idiom, because the checksum
already imports its scan set and verdicts from there — one core, no drift.

**The callsign gate judges only unresolvable tokens** (as today); the set is
what the resolver returned `null` for. The pure core gains
`unresolvableCitations(text, resolve)` so the swap is testable without the
filesystem, matching the export convention the tests cite
(`tests/ref-census.test.ts:9`).

## Migration — a re-expression, and one correction it could not avoid

Both baseline files are regenerated by `--write-baseline` in the same commit.
That tool grandfathers whatever the corpus currently holds, so the migration
owes a check that it **grandfathered nothing new**.

The **callsign** baseline migrated as a pure re-expression: 13 files and 17
citations before, 13 files and 17 tokens after, per file equal. Its own
forward reference behaved as documented — `BRF-COUNT-BASELINE-TOKENS` was an
unresolvable token until `reg-sync` registered this brief, then the gate said
`gone — prune with --write-baseline`, and the prune restored the total.

The **td-ID** baseline did not, and the reason is a defect the token shape
exposed: `main()` counted **citation-bearing lines**, not citations —
`lines[i].match(TD_ID)` takes the first match only — while the exported
`countIds()` that the tests assert counts them all (*"a citation-dense line
counts them all"*, `tests/td-id-lint.test.ts`). The gate under-counted by 31
citations. Measured at migration:

| | before | after |
|---|---|---|
| baseline entries | 96 files | 64 files |
| citation unit | **lines** | tokens |
| citation-bearing lines | 150 | 150 (equal in 63 of 64 files) |
| citations | — invisible to the gate | 181 |

The per-file check is against the old unit: citation-bearing lines equal the
old count for 63 of 64 files. The exception is `docs/state-colours.md`, 2
against 3 — a genuine prune, which the new gate reports as shrink. The 32
dropped entries are stale: 30 name briefs since archived out of the scan set,
and 2 (`briefs/INDEX.jsonl`, `docs/style-guide.md`) are now clean. The old gate
had been printing all 32 as *baseline can shrink* on every `just check`, and
nothing pruned them — an unread signal in a lint that fails only on violation,
which is the ratchet decaying into an allowance by inattention rather than by
verdict.

A legacy flat baseline is **refused loudly** (`readBaseline` throws on a numeric
value) rather than guessed at: a count cannot be decomposed into tokens, and a
gate that invents a token set from a total is a gate that has stopped meaning
anything.

## Scope

**In:** `scripts/td-id-lint.ts` (the core, the td-ID gate, the reader),
`scripts/callsign-lint.ts` (the corpus gate, the pure extractor), both baseline
files, both test files.

**Out:** `src/` comment scanning (the documented v2 boundary); the unpushed
message range (already token-exact — it names the offending callsign); the other
`{file: count}` lints (`date-lint`, `lexicon-lint`, `elision-monotone`,
`debrief-link-lint`) — same shape, different quantities, and none of them is a
citation namespace where a swap is a false green.

## Acceptance

1. A file that drops one baselined token and gains another at equal count fails
   **both** gates, naming the new token — the test that would have caught the
   hole, asserted against the pure core.
2. Every verdict the count baseline produced still holds: unbaselined file with
   a hit fails, over-count fails, stale entry is a shrink, at-baseline is ok.
3. Both baselines are token-shaped; the callsign migration is equal per file,
   and the td-ID migration is equal per file **in the unit the gate was
   actually counting**, with the unit change recorded above.
4. `just check` green.
