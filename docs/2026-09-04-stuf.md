## Architectural Specification: Dual-Pattern Window Management

This architecture strictly enforces physical separation between window management and text rendering. The viewer binary contains zero internal windowing code, relying entirely on existing execution environments.

---

### Pattern 1: Remote Virtual Canvas (Constrained Displays & Mobile)

* **Target Surface:** Smartphones, small tablets, SSH terminal emulators (Termius, Blink).
* **The Problem:** The physical screen lacks room for concurrent side-by-side tiling. Spawning floating OS windows on a 6-inch glass pane is an exercise in user frustration.
* **Mechanism:** The remote terminal multiplexer (`tmux`) manages geometry.
* Windows and panes exist as virtual buffers within a single persistent session.
* Actuating a two-digit reference spawns a new window or pane via the multiplexer socket.
* The user toggles between the full canvas and an isolated pane using the multiplexer zoom primitive (`prefix + z`).


* **Ergonomic Signature:** High focus, one-frame-at-a-time inspection, zero layout distortion, and survival across carrier drops.

### Pattern 2: Local Physical Canvas (Desktops & Tiling Workstations)

* **Target Surface:** Multi-monitor workstations, laptops running tiling window managers (i3, sway, bspwm, AeroSpace) or desktop terminals.
* **The Problem:** Latency over SSH packet round-trips ruins keystroke cadence, and remote shells have no native access to local monitor geometry.
* **Mechanism:** The local machine drives both rendering and placement.
* The remote server serves strictly as a block-storage pipe over SSH.
* The local viewer executes natively, consuming remote text via `stdin`.
* Actuating a two-digit reference issues a local process spawn call to the workstation's terminal emulator or window manager.


* **Ergonomic Signature:** Native DPI text rendering, zero-latency stepping, local hardware font scaling, and physical spatial persistence across real desktop real estate.
