# Am I doing this wrong?

*(A working coder's setup for AI agents, and why it might be backwards.)*

I've been using AI coding agents for a while now, and I've ended up somewhere I didn't expect. I want to describe it, because I genuinely don't know if it's right.

The shortest version: **I've stripped almost everything out of my setup, and the results are much better.** I want to know if that's a real finding or a fluke.

## What I actually do

I use a coding agent with no extensions, no MCP servers, no skills, no plugins. Nothing loaded up. The whole harness is: point it at a repo, tell it to run `just orient`, and let it work.

The loop is:

1. Orient
2. Do the job
3. Debrief
4. Start a fresh session for the next job

That's it. Every task gets a new session. I don't stuff the context window. I don't keep a long conversation going. The work lives in files and in a task database, not in the chat history.

It works. Not "it works okay." It works *better* than the heavily-tooled setups I was using before.

## How I got here

This didn't start as a philosophy. It started because I wanted a better markdown viewer than `glow`.

That's the whole origin. Not a method — a viewer. But to keep the agent from wandering off, I had to keep it on task, and to keep it on task I had to write down what the task *was*. So I wrote briefs. Then decisions. Then a lexicon. Then a debrief for every job. And at some point I noticed the writing wasn't just *recording* what we were doing — it was *holding* it.

Before that, I'd been fighting the opposite problem. In April 2025, agents would do anything *except* the work. Ask for the capital of France, get offered a hotel in Paris. So I wrote a constraint stack — an exclusion policy. Witchcraft, Thai cookery, cephalopod communication protocols: no, no, no. Then the models got smarter, and the list got shorter and more abstract. *"Gonnae no dae that"* became *"ask the Derrida question."*

So the direction of travel was: **we used to say what the work wasn't. Now we say what the work is.** And the record — the briefs, the decisions, the lexicon — turned out to be how you say what the work is.

## The uncomfortable question

Everyone I talk to is racing to add more. More MCP servers. More skills. More frameworks. More orchestration. More context.

I've been racing the other way, and I think my results are better. That's a red flag. Either:

- I've found something real, and the industry is adding complexity it doesn't need, or
- I'm doing something wrong and the good results are a coincidence, or
- I'm solving a smaller problem than everyone else, and my simplicity is just a consequence of scale I don't have

I honestly don't know which. So I'm going to describe the reasoning and ask.

## The thing I can't stop thinking about

Everything I've built is text in and text out.

Instructions in. Rendered text out. Over SSH, both directions. No JSON. No HTML. No rendered UI. No database-to-API-to-frontend pipeline. Just text streams with well-defined side effects.

And it composes. Tools fit together. I can point things at each other and they work, the way Unix tools do, because the contract is text.

Here's why I think this matters, and I'd like someone to tell me I'm wrong.

**Most of the modern web stack exists to compensate for human limits.**

A database, an API layer, a rendered frontend, a manufactured UI for interactions — that whole pipeline exists because a human at a browser needs a persistent visual surface, discoverable affordances, and a way to click things without issuing malformed commands. Every layer is a workaround for the fact that the user can only see one screen and can only point.

An AI agent doesn't have those limits. It reads text fine. It doesn't need affordances; it needs a specification. It doesn't need a rendered surface; it needs the source.

So when I hand an agent a browser-shaped stack, I'm handing it a machine built to compensate for a disability it doesn't have.

Am I wrong about this? Because if I'm right, it's a bigger deal than my repo.

## What I think falls out of it

If the constraint that shaped the stack has changed, the stack should change. Not get faster — *change*.

The things I've found myself doing:

**Text is the invariant, renderings are variants.** One canonical text. Terminal output, speech output, whatever else — all just cheap projections. If the text is right, the projections are right. If I'd fused them, I couldn't swap one out.

**The Unix composability comes back.** It was lost because the interface stopped being text and became a rendered object graph. Agents can read a complex text contract without needing it pre-chewed. So the composition works again.

**Small is a feature.** Bounded context. Fresh session. Known starting position. Nothing carried in memory that isn't written down. The state lives in files, and the chat is disposable.

**The substrate doesn't need hand-holding.** Every extension is a thing the agent must learn and a thing that can be wrong. I took them all out and it got better. Which suggests modern models are competent enough to use `git`, `just`, and a text file without a bespoke integration layer.

None of this is obviously new. Some of it is just Unix, and Unix is fifty years old. What's new, maybe, is that it *applies again* — because the thing that broke it (humans needing things rendered) isn't in the loop anymore.

## The part I'm unsure about

Here's what keeps me up.

**Concurrency.** "The text is the truth" fails when multiple writers hit it at once. I use git as the transactional layer, which is a database of a kind. Is that enough at scale? No idea.

**Partial failure.** Text over SSH is fine until the connection dies mid-write. The web stack has answers. Does the text stack? Not obviously.

**Discoverability.** A human finds things by looking. An agent finds things by being told — which works for one repo. Does it work for ten thousand tools? Unclear.

**Scale.** Maybe everyone else is building for enterprise codebases with hundreds of agents, and my small silo just doesn't have those problems. That would make my simplicity a consequence of my scale, not a discovery.

There's a fifth one, and it's the one that actually worries me. The record I keep — the briefs, the decisions, the lexicon — gives the agent a disposition. It holds the invariants and defends them. That's what I want. But the same mechanism that protects *good* invariants will protect *bad* ones. An agent that holds its ground can hold the wrong ground. The only safeguard I've found is that the standing to reject runs both ways: the agent can refuse me, and I can refuse the agent. I don't know if that's enough. I suspect it's the kind of thing you only find out the hard way.

So: am I over-engineering my workflows by stripping them back? Or is everyone else under-engineering theirs by adding?

## Why I'm writing this

I don't have a framework to sell. I don't have a course. I'm not launching anything.

I wanted a markdown viewer, and I got a method instead. Which means either the method is real, or I've spent a year documenting my own confusion. Both are possible.

If you're doing something similar, I want to know.

If you're doing something similar and it *failed*, I really want to know.

If you think I'm solving a problem that only exists because I work alone on small repos, tell me, and I'll stop.

The specific question: **is the heavy stack a necessity or a habit?**

Because I've removed it and my code still works.

I've put this in writing because I'd rather be told I'm wrong than find out slowly. That's the whole thing, really. Document it, and it holds. Or it doesn't, and then at least you know.

Either way, I'll write down what happens next.
